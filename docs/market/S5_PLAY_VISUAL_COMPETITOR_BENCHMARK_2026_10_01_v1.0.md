## Direct visual evidence patterns

### Pattern A — Raw UI proof
Seen strongly in Codenia-style / resizer listings:
- large screenshot of actual app UI;
- photo preview;
- dimensions/size controls visible;
- minimal marketing decoration.

Conversion implication:
- high credibility;
- weak emotional differentiation.

### Pattern B — Brand mascot / strong color system
Seen in Puma:
- black UI;
- yellow accent;
- cartoon mascot;
- highly recognizable identity.

Conversion implication:
- memorable;
- can feel less precise/professional for strict-form workflows.

### Pattern C — Big marketing headline + phone frame
Seen in adjacent compressor/resizer creatives:
- large uppercase promise;
- phone mockup centered;
- bright cyan/blue fields;
- percentage reduction claims.

Conversion implication:
- immediate scanning;
- often looks templated and claim-heavy;
- can create policy/trust risk when using universal reduction percentages.

### Pattern D — Before/after / numeric proof
Seen across compressor/resizer UI examples:
- original size versus output size;
- file-size savings;
- target input;
- result comparison.

Conversion implication:
- directly supports buyer confidence;
- strongest fit for our verified-result differentiator.

### Pattern E — Feature-grid / toolbox overload
Common among broad incumbents and newer niche apps:
- crop;
- resize;
- format convert;
- batch;
- signature/passport;
- storage saving;
- social presets.

Conversion implication:
- broad reach;
- weak single-job clarity;
- increased screenshot density.

## Strategic gap

Most competitor visuals sell one or more of:
- generic compression;
- storage saving;
- broad resize/edit toolbox;
- "exact KB" claims;
- government/exam/passport use cases.

Few visual systems make the verification logic itself the hero:
`TARGET LIMIT -> ACTUAL BYTES -> PASS / NOT_MET`

That is our strongest defensible creative territory.

## Revised screenshot architecture

The prior 6-screen plan is retained but sharpened after benchmark.

### #1 — VERIFIED RESULT
Tagline:
`Verify the final size`

Required UI:
- result photo;
- large human-readable size;
- exact bytes;
- target bytes;
- PASS inequality.

Reason:
Competitors often show controls or generic compression first. We should lead with proof.

### #2 — SET THE LIMIT
Tagline:
`Set your KB limit`

Required UI:
- real selected photo;
- CURRENT size/dimensions;
- preset limits;
- Custom.

### #3 — SAVE / SHARE
Tagline:
`Save or share the verified file`

Required UI:
- PASS result;
- Save;
- Share;
- Before/After if legible.

### #4 — CUSTOM LIMIT
Tagline:
`Use a custom KB or MB limit`

Required UI:
- numeric input;
- KB/MB selector;
- decimal guidance.

### #5 — PRIVATE CORE PROCESSING
Tagline:
`Photo compression stays on-device`

Required UI:
- Home or Processing;
- original-untouched cue;
- no whole-app "offline" promise after AdMob.

### #6 — HONEST NOT_MET
Tagline:
`No false PASS when the target is too small`

Required UI:
- NOT_MET;
- actual bytes > required bytes;
- calm retry guidance.

## Icon benchmark implication

Do:
- preserve Compression Frame Mark;
- strengthen inward / fit-to-limit cue for the 512 store icon;
- keep Warm Ivory + Deep Ink/Teal;
- preserve negative space.

Do not:
- use mascot;
- use "KB" lettering;
- use checkmark as main mark;
- use generic crop-corner-only semantics;
- copy competitor gradients or blue utility icon conventions.

## Feature graphic benchmark implication

Recommended direction:
- no device frame;
- no mascot;
- no giant percentage claim;
- no feature-grid collage;
- one visual sentence:
  `large/source photo -> limit cue -> smaller/result photo -> verified state`
- text-free preferred; if text is used:
  `Set a limit. Verify the result.`

## Visual differentiation thesis

`QUIET PROOF > LOUD PROMISE`

Our listing should feel:
- calmer than Puma / bright-blue utility competitors;
- more precise than generic resize tools;
- more trustworthy than universal "exact KB guaranteed" creatives;
- simpler than feature-grid competitors;
- more premium than raw QA screenshot dumps.
